# Investigation evaluation and results

The fixed dataset and evaluator live in `investigation/tests/test_phase7_evaluation.py` and run against the Investigation API plus the disposable tmpfs PostgreSQL test service. Dataset version: `traceforge-investigation-phase7-v1`. The suite prints a `PHASE7_EVALUATION=` JSON record so results can be captured without writing files into the repository.

## Scenario dataset

The current v1 dataset is a bounded investigation-contract evaluation, not a broad application fault simulator. Its ten cases cover unknown incidents, health current/stale/missing, trace current/unavailable, Order current/partial/unavailable, compensation contradiction, and resolved recovery. Inputs use fixed in-process source clients, and database state is isolated in the tmpfs Compose test profile. The suite records the single known cause available in this dataset; broader payment-delay, inventory-failure, retry, and live-service outage scenarios are not represented by this run.

## Metrics

- **Top-1 root-cause accuracy:** investigations whose first ranked cause matches the scenario's labeled cause divided by evaluated scenarios with a determinate label.
- **Top-3 root-cause recall:** determinate scenarios where the labeled cause appears among the first three candidates divided by determinate scenarios.
- **Evidence-reference validity:** cited evidence IDs present in the bounded evidence package divided by all cited IDs.
- **Unsupported-claim rate:** claims labeled as factual that cannot be supported by retrieved observations divided by reviewed factual claims. Report the review method and sample size.
- **Investigation latency:** wall-clock time from request acceptance to persisted report; report sample count and percentiles.
- **Cost per investigation:** provider-reported or calculated token cost only when provider pricing and token counts are available. Otherwise report as unavailable.

Publish dataset version, counts, timestamp, environment, excluded cases, and limitations with every run. An ambiguous case is not scored as a failure when a well-grounded investigator abstains as designed; report abstention behavior separately.

This run supersedes earlier recorded runtime and latency values. The fixed dataset has 10 API cases: an unknown-incident request (404), current/stale/missing service observations, successful/unavailable trace reads, current/partial/unavailable Order reads, an open incident contradicted by fully compensated decline evidence, and a resolved recovery with explicit terminal/compensation evidence. The evaluator separately checks that a fresh UP probe yields no finding and a confirmed order returns the exact `RESOLVE` decision, no finding, and zero incident rows when there was no open episode. Per-scenario assertions check source freshness, uncertainty wording, result completeness, expected evidence gaps, citations, and facts. Repeated API requests replace the latest snapshot, and concurrent requests leave one snapshot per incident.

- **Citation validity:** 47/47 references (1.0).
- **Unsupported factual claim rate:** 0/26 (0.0), using a fixture-backed oracle that checks each fact's cited typed evidence and exact generated wording. This is an automated scenario review, not an independent blind human review.
- **Persisted API latency:** latest 10 request runs, p50 **38.943 ms**, p95 **42.629 ms**, measured around an in-process ASGI POST through PostgreSQL persistence. Upstream sources were deterministic in-process fixtures, so this is not an end-to-end production latency estimate or SLO.

The 10 API cases include one unknown-incident 404 and nine persisted investigation scenarios; a repeat adds one successful POST, for 10 measured report runs and nine latest snapshots. The unknown-incident request writes no report. The healthy UP and confirmed-order rule checks produce no finding. Investigation requests did not change incident status or occurrence count.

Resilience behavior in the automated suite used controlled component fault injection: Order client timeouts/partial responses, malformed and oversized responses, trace/Tempo client unavailability and invalid/oversized summaries, injected provider unavailability, and PostgreSQL persistence failure. Cycle `f1c185bb-8b3c-4f3d-a9ee-c66c73e08f3f` observed the next failed probe and exactly one `SERVICE_NOT_READY` incident (`e1474a0e-fbdb-4cc2-8e4f-fbb1b6ad576e`). - **Order and Investigation outages:** a local-only payment-decline/compensation failure returned HTTP 503 with `COMPENSATION_REQUIRED` and `inventoryReleased=false`. The Order source became stale while its last successful observation remained unchanged and its recovery incident stayed open. During Investigation downtime Gateway health stayed HTTP 200 while incident/detection proxy reads returned HTTP 503. Restarting Investigation retained the stale source timestamp and the same open incident. Restarting Order allowed the real recovery worker to release inventory; the order reached `FAILED` with `inventoryReleased=true`, and the same `ORDER_RECOVERY_STALLED` incident (`60f2ebaf-f639-4873-a71e-560930ba9456`) resolved.
- **PostgreSQL outage:** Investigation readiness returned 503, liveness returned 200, and detection status returned 503 with `DETECTION_STORE_UNAVAILABLE`. After restarting disposable PostgreSQL, readiness recovered and the incident plus `order-attention` last-success timestamp remained persisted/non-regressing.
- **Tempo outage:** trace lookup returned HTTP 503; investigation returned HTTP 200 `PARTIAL` with `TRACE_SOURCE_UNAVAILABLE`; detection completed and the existing incident status/count did not change. Tempo uses tmpfs, so the test created a new successful order after restart with a caller-supplied trace ID and verified a queryable trace containing `api-gateway`, `order-service`, `inventory-service`, and `payment-service` spans.
- **Collector outage:** a new detection cycle completed and the stored Tempo trace remained queryable with HTTP 200; incident state/count did not change. The Collector was restored.

The harness initially exposed two verifier/runtime defects: Tempo's root-owned tmpfs prevented its non-root process from creating blocks, and the verifier incorrectly treated `occurrenceCount` as a health-probe streak. The template now sets the Tempo tmpfs owner to UID/GID 10001, and the verifier asserts distinct completed health cycles and incident state. A further run showed that PostgreSQL tmpfs cannot retain data across a container stop; PostgreSQL now uses one uniquely named volume per random outage project. Cleanup verifies that volume's exact name and Compose labels and removes it only after its containers detach. Tempo remains tmpfs-backed. The final run left no containers, network, images, or PostgreSQL volume for its project. Post-run inspection found the same nine healthy default containers and unchanged volumes (`traceforge-postgres-data`, `traceforge-tempo-data`, and `traceforge-maven-cache`) as before the experiment. The verifier compared source timestamps across restarts; raw timestamps and the generated trace ID were not emitted, and no full successful-run service-log bundle was saved. The failed Tempo startup log was captured during diagnosis.

`docker compose config -q`, the harness `-PrepareOnly` resolved-isolation validation, and `git diff --check` passed. The latest Investigation run passed 72 tests in 4.62s.
