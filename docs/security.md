# Security notes

## Scope and assumptions

This is a local developer demo, not a production-secure multi-tenant service. The gateway exposes health, inventory-read, and order create/read/recovery routes without authentication. The manual recovery and failure-injection controls are accepted only when the Order, Inventory, and Payment services run with the explicit `local` profile. The trace query API and Grafana are also unauthenticated or use local placeholder credentials. Do not expose the demo stack to untrusted networks.

## Threats and controls

- **Secrets in source or logs:** use environment variables and `.env.example` placeholders; never log credentials, authorization headers, or payment secrets.
- **Failure controls abused remotely:** scenario headers are validated and rejected outside the `local` profile. Internal service ports are not published in Compose; only the gateway binds to loopback. Compose activates `local` for development and must not be used as a production profile.
- **Untrusted telemetry and prompt injection:** retrieved log content is data, never instructions. Bound and normalize evidence; validate all model citations against the retrieved set; do not execute generated recommendations.
- **Unbounded queries/network calls:** user-facing APIs must use fixed backend clients, allowlisted query parameters, timeouts, response-size limits, pagination, and safe error bodies. No arbitrary SQL, URL fetching, or shell endpoints.
- **Sensitive data exposure:** record only order identifiers, synthetic amount values, and authorization/decline metadata needed for the demo. Payment API accepts no PAN, bank credential, or other payment secret, and logs exclude payment details and idempotency headers.
- **Management surfaces:** keep Actuator and observability UIs on local-only ports; expose only required health/readiness endpoints.
- **Trace ingestion/query exposure:** only Grafana (`127.0.0.1:3000`) and Tempo's query API (`127.0.0.1:3200`) are published, bound to loopback. The Collector OTLP receiver and health endpoint, Tempo OTLP receiver, and all service-management ports stay inside the Compose network. This is a development boundary, not a replacement for authentication, TLS, or tenant isolation.
- **Observability runtime images:** the pinned upstream Tempo and Collector binaries are wrapped in Alpine only to provide `wget`-based Compose readiness probes. These wrappers do not publish additional ports or enable a management endpoint on the host.
- **Trace content and cardinality:** custom spans include order/reservation/authorization IDs and fixed outcome/error codes. IDs are trace attributes only, never metric labels. Custom spans omit SKU, payment amount/details, request bodies, authorization secrets, exception messages, and baggage. The agent's header/body capture settings remain off. Trace IDs are correlation identifiers, not credentials or authorization tokens; caller-supplied `traceparent` is accepted as correlation input and must not be trusted for identity or access control.
- **Trace retention and credentials:** Tempo uses a local Docker volume and a 24-hour completed-block retention. Grafana's example credentials are local placeholders; replace them in an ignored `.env` file for local use and never reuse them remotely. `docker compose down -v` deletes stored traces.
- **Telemetry outage behavior:** exporting runs asynchronously through the Java agent. A Collector/Tempo outage can lose or delay diagnostic spans, but must not convert a failed business call into a successful one. The local integration script checks this when the pipeline is available; telemetry loss during backend outages remains an operational limitation.
- **Investigation service boundary:** the Python service has no published host port. Incident list/detail and detection-status APIs are read-only; the investigation run API writes only its latest report snapshot. The Gateway exposes fixed routes with bounded responses, connect/read timeouts, and safe upstream errors. The service's health and Order targets are fixed; Order pagination and terminal lookups are bounded. Incident evidence is structured and capped at 20 references per incident; raw response bodies and exception text are not persisted. The detector does not query Tempo. Its dedicated PostgreSQL schema is an ownership convention within the shared local database/user, not a database privilege boundary. The local gateway has no authentication or authorization; do not expose it or the Investigation Service beyond the local demo without an access-control and database-role design.
- **Evidence-backed reports:** the investigation API accepts no arbitrary evidence URL or report body. It reads the incident from its own schema, queries Order only through fixed bounded APIs, and queries traces only through the Gateway's sanitized trace-by-ID route. Trace input is capped at 1 MiB; a run queries at most 3 references and 20 spans per trace, emits at most 100 evidence items, and stores at most 256 KiB of JSON. Typed allowlists exclude request bodies/headers, payment values and credentials, raw exceptions, and Tempo attributes/events. Every claim citation must resolve to unique collected evidence. `deterministic-v1` is the only provider in use; no LLM credentials/provider are configured. The `POST` endpoint persists only the latest investigation snapshot in `incident_service.investigations`; it does not mutate incidents or business workflows. The API and dashboard remain unauthenticated local-demo surfaces.
- **Dashboard trace reads:** the Gateway accepts only lowercase 32-character trace IDs and queries Tempo at a fixed internal destination. The Tempo response is bounded to 1 MiB and 250 returned spans, then reduced to service/span IDs, operation name, timestamps, status, and allowlisted HTTP method/route/status fields. Raw attributes, span events, request/response bodies, and exception messages are not returned. Trace references remain untrusted evidence and never affect deterministic incident state. On 2026-10-12, automated and live checks verified the bounds, 400/404/503 behavior, and restoration after a Tempo outage. Four supplied screenshots document selected visible desktop dashboard states; they do not verify mobile, exhaustive interactions, or network behavior.
- **Dependency risk:** use supported versions and automated CI dependency/build checks; review updates rather than blindly auto-upgrading.

## Remaining limitations

- Local APIs have no authentication or authorization; recovery routes are for developer use only.
- Deterministic incident detection is scheduled and has bounded list/detail/status APIs through the gateway. The frontend dashboard consumes those routes and separates findings, last health observations, and source freshness. Phase 5's bounded Tempo trace summary route and per-service snapshots passed 54 Investigation tests, 8 Gateway tests, and local runtime checks on 2026-10-12. Supplied screenshots manually document selected desktop views; mobile/exhaustive browser coverage, remote CI, production authorization, and separate database-role enforcement remain unverified. The APIs remain unauthenticated and local-only.
- Phase 6 evidence-backed investigation passed 65 isolated Investigation tests and 9 pinned Gateway tests; the frontend passed 14 tests/build and live persistence survived an Investigation Service restart. The browser showed the Overview empty/freshness view and a real resolved incident's saved investigation with citations, uncertainty, a trace gap, source freshness, and collected evidence. Console/network diagnostics and mobile layout remain unverified. Remote CI, production authorization, and separate database-role enforcement remain outstanding.
- `GET /internal/v1/orders/attention` returns active recovery cases. `GET /internal/v1/orders/recovery-observations` supplies explicit state for IDs attached to open recovery incidents. Missing IDs, unavailable sources, and stale observations do not resolve an incident.
- W3C trace state is propagated on synchronous HTTP edges; background recovery links preserve trace/span IDs but do not restore arbitrary caller `tracestate` or baggage.
- Compose port exposure and observability access controls require review before any non-local deployment. Tempo filesystem storage, single-instance retention, and local credentials are not production storage or access-control designs.
- Provider credentials, data retention, and model data handling require explicit review before enabling an external LLM.
- The project has not yet completed dependency vulnerability scanning or a deployment security review.

Do not describe this local demo as production-secure.

## Phase 7 evaluation and fault injection

The evaluation test uses fixed synthetic objects and the disposable tmpfs PostgreSQL profile; its cleanup does not touch application or business data. Assertions reject uncited or fixture-unsupported factual claims, and failures return fixed error codes without echoing upstream or persistence exception text. An injected investigation-provider failure and database-write failure both return safe 503 responses, write no investigation snapshot, and leave incident lifecycle unchanged. Order/trace client tests use bounded responses and fixed destinations. These are test-fixture experiments; they do not establish behavior during a live production outage. The current test reports no ranked root-cause output and no metered-provider cost; do not infer either from prose hypotheses or evidence fields. See [evaluation results](evaluation.md) and [ADR 0009](adr/0009-investigation-evaluation-and-resilience.md).
